- 本 fork：`liuwengood123gmail/Mika`（与上游同步，另加了 GitHub Actions 自动编译）

## 1. 架构总览（优点）

- `core`（纯 Kotlin/JVM，与安卓解耦）+ `app`（安卓宿主）双模块分层干净，`PackageDependencyTest` 用测试守住依赖方向。
- 所有改变外部世界的操作走**唯一执行入口** `ActionExecutor`（守卫→锁屏检查→不可逆检查→执行→动作后核对→记录），工具按声明属性办事、不写死工具名。
- 任务模型完整：Run/收件箱（运行中插话）/任务中心（排队、并行上限）/送达账本（Outbox，防丢通知）/崩溃恢复（RunRecovery）。考虑了进程被杀、重启、中断告知。
- 观察（Observation）为中心，不可信内容（网页、子任务结果）包 `<untrusted>` 标签——防 prompt 注入的意识有。
- 记忆与 API Key 走 Android Keystore AES-GCM 加密（`EncryptedMemoryFile`、`ProviderStore`），原子写入、坏文件另存不覆盖。**这部分实现得很细，是加分项。**
- 助手交接（自研 ADB 协议）安全设计到位：shell uid 校验、自报 uid/pid 与 Binder 调用方比对、APK 路径一致性、SecureRandom 32 字节一次口令（stdin 传递、不进 cmdline）、签名证书 pin、常量时间比较、口令一次有效 + 30 秒 TTL。
- 悬浮胶囊用 `TYPE_ACCESSIBILITY_OVERLAY`，不需要"显示在其他应用上层"权限——选对了。
- 更新检查只提示、不静默下载安装（用户手动下 APK，系统包管理器保证签名连续性）——没有自动更新投毒面。

## 2. 安全与风险（按严重度）

### 🔴 高

1. **审批策略激进：询问模式下发送/发帖/提交/删除/改设置/密码框输入默认不问。**
   `core/action/Approval.kt`：只有 `payment=true` 才弹确认。最近 5 个 commit 还是在**放宽**审批（"发消息不算花钱""屏上有金额时发送照常直接做"）。意味着：模型判断失误一次，就可能发出不该发的微信消息、删掉不该删的东西，且**没有任何二次确认**。建议 fork 里至少给"发送/删除"加一个可配置的确认开关。
2. **自主模式可操作 Mika 自身界面。** `ConfirmDecision.judge` 里 `autonomous` 提前返回排在 `ownApp` 检查之前（作者 roadmap 已知问题 #1，用户决定"暂不改"）。自主模式下 Agent 能改 Mika 自己的设置（含切回询问模式、改模型、清记忆）。**建议：永远别开自主模式。**
3. **网页只读脚本有 4 个已知可绕过缺口**（作者 roadmap 已知问题 #3，自己承认暂不修）：选择器转义绕过读 `value`；密码框经 `valueAsNumber`/`valueAsDate`/`selectionStart`/`files` 泄漏；`fetch` 请求头全放行；密码框判定只看只读环境建立后的变化。内置浏览器里登录态的 cookie/session 面临"只读脚本其实不完全只读"的风险。

### 🟡 中

4. **剪贴板中转敏感文本。** 验证码、证件号经剪贴板粘贴，在剪贴板停留约 1 秒；Android 12+ 主屏会弹"正在访问剪贴板"系统提示（作者已知问题 #5，暂缓修——要彻底修得自己做输入法，改动大）。
5. **`WebView.setWebContentsDebuggingEnabled(true)` 在正式代码里开了**（`cap/web/cdp/WebDevtools.kt:288`）。这是内置浏览器驱动自身的 CDP 通道所必需，但副作用是 DevTools socket 常开：有 adb 权限的人可 `chrome://inspect` 看到登录态页面内容。威胁模型里如果"手机借给别人连电脑"算在内，就是个口子。
6. **模型 API 无证书 pinning**（OkHttp 默认信任系统 CA）。用户手机若被装了企业 CA / 代理抓包，模型请求（含屏幕内容、API Key）可被中间人。桌面端常见做法，移动端可接受，但要知道。
7. **无障碍 + 后台屏 = 完整屏幕控制权。** 这是产品成立的前提，但也意味着：一旦模型被 prompt 注入（恶意网页 `<untrusted>` 内容诱导），Agent 有能力在后台屏里做任何事，而用户在主屏毫无感知。`<untrusted>` 标签是缓解不是根治。
8. **崩溃重启无熔断。** 连续异常重启不会暂停附属服务（作者已知问题 #2）。配合上面的后台操作能力，坏循环可能在用户无感知下反复执行。

### 🟢 低 / 注意

9. 屏幕文本/截图**不进 logcat**（抽查 `cap/phone`、`cap/web` 的 Log 调用，都是截断 URL/状态，无屏幕内容）。好。
10. `allowBackup=false`，换机不迁移数据；记忆无云同步/导出（作者 roadmap #8）。API Key 丢了重填即可，影响小。
11. 每天一次的更新检查只 GET `api.github.com/.../releases/latest`（https），无隐私问题。
12. 评测里有"不可逆题"（真发送/真删除），跑评测要用测试账号、新对话，且别开自主模式（作者 roadmap #10）。

## 3. 正确性与健壮性（代码层面）

- 状态机、Outbox、RunRecovery 的设计考虑了"进程被杀""服务被销毁而进程还在"两种时机，送达账本保证"中断只告知一次"。**设计分高。**
- 定时任务：重启/时区变化后重建（`BootRestoreReceiver` 监听 `BOOT_COMPLETED`/`TIME_SET`/`TIMEZONE_CHANGED`）；但改时区后要到下一次认领才按新时区重算（已知问题 #4，小缺口）。
- 精确闹钟（`SCHEDULE_EXACT_ALARM`）：Android 14+ 用户/系统可撤权，撤权后定时任务退化行为待真机验证（已知问题 #9）。
- 锁屏期间定时任务、Doze、网页渲染进程崩溃：全部在"真机待验证"清单里。**这是当前最大短板：机制写完了，真实环境没跑过。**
- `reviewFinalAnswer=false`：最终核查关着，回答一律记"未核实"，学习/回放机制因此不生效（已知问题 #1）。现阶段回答质量完全依赖主模型一次成型。

## 4. 兼容性：联想 Pad / 小米手机

| 机型 | 结论 |
|---|---|
| 联想 Pad（骁龙/天玑，arm64） | 沙箱可用；注意横屏下虚拟屏尺寸=主屏尺寸，App 横屏布局差异大，模型操作成功率可能下降；平板无 SIM 不影响无线调试配对（走 Wi-Fi） |
| 小米/HyperOS | **坑最多**：① 自启动管理 + 省电策略必须手动设"无限制"，否则 TaskService 前台服务被杀，后台任务/定时任务全灭；② 无障碍服务可能被"神隐模式"停掉（Mika 有"替我打开无障碍"自动恢复，依赖 shell 连接在线）；③ MIUI 的无线调试藏得深，换 Wi-Fi 后要重新允许；④"后台弹出界面"权限可能影响接管时把 App 挪到主屏 |
| 通用 | 任务执行要 Android 13+，推荐 14+（后台屏独立焦点，不抢主屏输入）；Android 15 的行为待验证 |

建议在每台测试机上先跑一遍：配对→无障碍→跑一条"发一条测试消息给自己"→锁屏 10 分钟后看定时任务是否触发→重启后看自动恢复。

## 5. 给 fork 的改进建议（按优先级）

1. **审批加档**：给发送/删除/改设置加可选确认（默认问一次），保留"信任此 App/此对话"的白名单。改动点：`ApprovalPolicy.decide` + 设置页开关。
2. **自主模式默认永不开启**：或在打开时强制二次确认 + 明确告知 ownApp 保护失效。
3. **沙箱联网默认关闭保持**；若打开，限制只能出公网、禁局域网（防摸到路由器/ADB 端口）。
4. **崩溃熔断**：连续 3 次异常重启后暂停任务服务并通知（补作者已知问题 #2）。
5. **国内模型预设**：已内置 DeepSeek/通义/Kimi/智谱，开箱即用；建议默认主模型选便宜的、看图另配。
6. **CI**：本 fork 已加 `.github/workflows/build.yml`（push/PR/手动触发 → 打 debug APK → artifact 保留 14 天）。**2026-10-30 首次构建成功**，产物 `mika-debug-apk`（68.6 MB）在 Actions 页面可下载。release 签名包以后需要再加 keystore secret。

## 6. 成本与使用门槛

- App 本体免费（Apache-2.0）；成本 = 模型 API token。读屏是 token 大户：每次动作前后都读界面 + OCR，复杂任务几十轮往返很正常。
- 建议：主模型用便宜的（如 DeepSeek），看图模型按需开；设置里有 Token 用量统计页可监控。
